## 1. Why additional local remediation is mandatory

The [independent QA](https://github.com/zyyu1/literature-management-system/pull/2#issuecomment-7089087597) observed:
- **Q1 (integrity blocker; non-waivable for locally certified export)**: `poc/001/src/safe-api.mjs` `listRecords` walks only kind collections returned by root PROPFIND. A well-formed root listing omitting `projects/` (which has a record) still yields `200 ok count 1`; a duplicated record `href` gives `200 ok count 3` although two stored records exist, and the resulting bundle fails its own restore's uniqueness check. This is residual **P2-N1**: a green suite covering malformed XML cannot waive *known* completeness and multiplicity failures.
- **Q2 (Fence terminal-safety hardening)**: `handleFence` trusts the PUT response's different strong ETag to issue terminal `not_committed` **without GET read-back**. An independent non-conforming provider double returned a misleading strong PUT ETag; the storage still used the old content-hash ETag, allowing a delayed original PUT to commit after the cached `not_committed`. This is a residual **provider-conformance dependency** despite locally fixed P1-R1 under conforming mocks.
- **Q3 (documented-contract discrepancies)**: `poc/001/README.md` still states replay "never re-sends" absolutely; code default global cap is `maxPerPrincipal (1000) * principalCount`, not always 10,000, and common refusal is `principal_ledger_full`; old write-tag prose omits HMAC authentication and provenance. A saved operation replayed after protection-window expiry can yield `412 conflict` without explanation. **Documentation must describe observed bounded guarantees, not ideal guarantees.**
- **Q4/Q5 (documented P2 residuals, not new features approved)**: saturated one-principal Unknown slots may be stuck until restart; misconfigured `maxLedgerEntries < sum(principal quotas)` can cause cross-principal starvation; slow inbound body can retain a pending reservation until the underlying server's request timeout. A Fence PUT that becomes UNKNOWN and later applies can strand original verification `indeterminate` without a supported safe recovery procedure. Document/mark **UNSUPPORTED/LIVENESS-LIMITATION**; do not silently redesign durable ledger, inbound server timeout or provider-fencing protocol.

**Critical distinction:** success under a mock is bounded **TESTED_SYNTHETIC** evidence, not an atomic snapshot, provider-certified listing completeness, RFC/real Nutstore compliance or real backup/restore certification. A well-formed provider listing can omit an *individual unknown file* without a manifest/snapshot oracle; the three-known-kind check guards the specific observed omission but does **not** prove arbitrary provider completeness. State this explicitly in reports.
