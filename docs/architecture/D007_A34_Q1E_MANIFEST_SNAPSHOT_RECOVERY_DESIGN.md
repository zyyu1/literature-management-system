## 2. Three different mandatory proofs

**Inventory completeness:** an independently trusted authoritative record inventory must cover **all** logical IDs of a confirmed owner-scoped dataset. A PROPFIND result and a catalog rebuilt by re-listing that same untrusted response are not independent authority. Unknown omitted records cannot be detected without an independent source of expected identities.

**Point-in-time snapshot:** all record revisions, relationships, confirmed deletes and cross-object histories must map to the *same* durable checkpoint or independently proven quiescent/fenced writer boundary. A sequence of successful GETs with hashes can mix versions; unresolved delayed/UNKNOWN writes prohibit certification.

**Freshness/anti-resurrection:** a valid signed/encrypted old backup can still be stale. A **separately protected latest monotonic checkpoint/deletion witness** outside the rollback domain of the archive must establish which IDs were later confirmed deleted and which changes superseded the archive. No timestamp or self-declared archive sequence is sufficient by itself.

Failure of any needed proof ⇒ **`NON_ATOMIC / EXPORT_INCOMPLETE / NOT_RESTORE_CERTIFIED`**; never `COMPLETE_BACKUP`, `RESTORE_CERTIFIED` or active overwrite. A synthetic fixture's known count is not proof of all unknown production data.

## 3. Conditional architectural decisions (A34-Q01..Q08)

### A34-Q01 — Trusted authoritative inventory (conceptual, NOT implemented)
A future inventory/commit record must authenticate `ownerScope`, schema/catalog version, opaque logical record IDs, entity types, scoped Zotero compound identity (`zoteroLibraryType, zoteroLibraryId, zoteroItemKey`), confirmed opaque record revisions, parent-child edges, entity/total cardinalities, state and **confirmed deletion events** and trusted checkpoint ID. The inventory update must be consistent with each confirmed create/edit/unlink/Project-delete/Quote Relink and source-history append; separate record PUT then manifest PUT (or opposite order) is *not* an atomic protocol. Backend, signing authority, transaction/commit log, canonical record naming and CAS remain **UNSELECTED**. No authoritative inventory can be derived solely from a possibly incomplete PROPFIND. If no safe inventory transaction/witness can be proven, **STOP and request storage architecture amendment**; do not silently choose PostgreSQL or claim provider supports transactions.

### A34-Q02 — Consistent checkpoint and writer fence (conceptual)
A future `snapshotId` must pin one authenticated catalog/checkpoint and every record revision. Only a proven coordinated read snapshot or separately authorized quiescent/fenced checkpoint **across every writer/device and deletion/manifest path** can certify consistency. Admission/writer stop cannot infer absent in-flight late writes from a quiet connection. A5 `UNKNOWN` requires reconciliation by authoritative operation identity or quarantine; never auto-resolve by read matching bytes. Reject mixed revisions, an omitted **known** ID, a duplicate, foreign owner, missing parent, truncated/unordered SourceHistory, stale association or incomplete import. Record failure while preserving last-confirmed records and drafts.

### A34-Q03 — Authenticated versioned manifest contract (logical, not physical)
A future manifest must bind `exportFormatVersion`, independently versioned `manifestVersion`, each record `schemaVersion`, `snapshotId`, exact owner/namespace, trusted `checkpointId`/monotonic high watermark, diagnostic exportedAt, declared scope/exclusions, full trusted inventory/record identity+revision+parent mapping, counts by type, hash/length of every canonical serialized byte sequence, aggregate authenticated commitment, deletion witness/coverage reference, and explicit missing/UNKNOWN markers. UTF-8 Markdown bytes, code fences, Unicode/LaTeX, whole-note five-field aggregate and Quote SourceHistory must be **lossless**. Per-record SHA-256 is an accidental corruption check, **not** issuer authenticity; authentication requires a separately trusted MAC/signature or approved authenticated encrypted manifest with owner/key/version/AAD binding. Canonical JSON byte profile, Merkle/hash tree, crypto algorithm, archive packaging, filenames and KMS are **TBD by future G1**. Protect metadata (IDs, titles, relationships, excerpts) from plaintext disclosure; no user PDFs or secrets.

### A34-Q04 — Deletion witness and anti-resurrection (CONDITIONAL)
A7 minimal tombstone is **not a deployed feature**. Only **explicitly confirmed** permanent Project deletion/association unlink can produce scoped protected deletion evidence; Project archive is reversible and cannot be treated as deletion. No deletion cascade to shared global Note/Quote. Future minimal marker should contain only scoped opaque ID, event/revision/operation identity, a protected ordering and **no deleted body text**. Marker creation and deletion must share a proven atomic/fenced state boundary: `DELETE` then `marker PUT` and the opposite order both have crash gaps on multi-file WebDAV. Latest accepted deletion/checkpoint witness must be stored or verified in a **different trust/rollback domain from the old backup**. Old archive with a later deleted Project, a missing/mismatched high watermark or uncertain marker coverage ⇒ `RESTORE_BLOCKED_STALE_DELETION_STATE` / `DELETION_WITNESS_UNVERIFIABLE` and no live cutover. Never silently reuse a deleted ID, erase global Notes, forge deletion certainty, or retain markers indefinitely without a separate privacy/retention decision. Downloaded user exports cannot be remotely revoked.

### A34-Q05 — Protected backup keys and authenticity
Recovery/backup keys need separate purpose and authority from live DATA-KEK, Session, MFA and external Zotero/WebDAV secrets (A17). Access to `BACKUP-KEK/DEK` must require independently approved Owner recovery/step-up and key custody. Restore rejects wrong owner, key version, nonce/tag/AAD, truncated or unauthenticated manifest; invalid backup is not an empty Note. Lost keys ⇒ `KEY_UNAVAILABLE`, potentially `UNRECOVERABLE`; password reset cannot reconstruct unknown random material. AEAD validity is not a latest-version witness. No algorithm choice, key creation, escrow deployment, crypto erase or actual archival is authorized.

### A34-Q06 — Isolated staging and read-only dry-run
After a **future separate restore authorization**, authenticate scope/intent; validate manifest signature/authentication, supported versions and limits, exact inventory/revisions/counts/hashes, canonical Zotero owner/type/key, relationship closure, one shared Note/status per paper, ordered confirmed source history, deletion witness and key recoverability. Reject zip-slip, symlinks/traversal, unsafe URL/path, bombs/oversized JSON, unsupported schema and cross-owner mappings. Stage exclusively to **new isolated namespace**, never direct PUT into live data. Run a read-only graph consistency/dry-run compare, preserve active last-confirmed dataset, local drafts and all UNKNOWN operation evidence. A note's field text is compared byte-for-byte; never auto-merge stale history or overwrite newer verified revisions.

### A34-Q07 — Separate cutover and rollback authority
Even validated staging is **NOT** authorization to restore active data. Active cutover requires its own precise user/Design high-risk G1 and independently proven atomic namespace swap or equally safe fenced pause, verified tombstone/high-watermark update, idempotent state mapping, rollback plan and exact SHA independent QA. If cross-object/ledger durability and cutover cannot be proven on chosen backend, **STORAGE_ARCHITECTURE_AMENDMENT_REQUIRED / STOP**, not a best-effort copy marked “Restored”. RPO/RTO and restoration SLO remain UNDECIDED.

### A34-Q08 — Truthful status taxonomy, without modifying API/frozen UI
Current: `DESIGN_ONLY_Q1E / UNSUPPORTED_COMPLETENESS / NOT_RESTORE_CERTIFIED`. Potential later evidence states (not achieved): `KNOWN_FIXTURE_ENUMERATION_OBSERVED`, `SNAPSHOT_CERTIFIED_SYNTHETIC` after independently proven catalog+checkpoint, `RESTORE_CERTIFIED_SYNTHETIC` only after full isolated recovery and anti-resurrection tests, `PROVIDER_OBSERVED` only after separate ACCESS-02, `PRODUCTION_RESTORE_CERTIFIED` only after independently tested provider atomicity, operations and separate Design approval. Existing A17 failure states `MANIFEST_INCOMPLETE, SNAPSHOT_INCONSISTENT, RESTORE_BLOCKED_STALE_DELETION_STATE, KEY_UNAVAILABLE, UNRECOVERABLE` remain proposed recovery states and do not alter A5 write outcomes or frozen three-state ReadingStatus.
