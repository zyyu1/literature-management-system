## 2. Target capability and non-negotiable invariants (A36-I01..I10)

1. **I01 completeness:** trusted owner-scoped catalog enumerates every **confirmed** logical ID/revision/parent and confirmed delete at a pinned checkpoint; never self-generates from the potentially incomplete DAV listing. Unknown omitted record requires an external authoritative oracle or **UNSUPPORTED**.
2. **I02 consistent cut:** every exported record, association, Quote/SourceHistory and tombstone must match the same independently observed commit/checkpoint. If mixed, incomplete, stale or uncommitted ⇒ `SNAPSHOT_INCONSISTENT/NOT_RESTORE_CERTIFIED` and **zero certified bundle**.
3. **I03 confirmed mutation atomics:** Project deletion + only its ProjectAssociations/Important + protected deletion marker and Quote Relink + history append must be all-or-nothing/linearizably fenced for their declared operation scope; never alter shared global Note/Quote by Project deletion.
4. **I04 crash truthfulness:** before commit, after commit before ACK, lost ACK, process death and restart must never fabricate `CONFIRMED` or `DEFINITE_FAILURE`. A5 `UNKNOWN` retains its nonterminal semantics unless an independently valid durable operation witness establishes its specific result; do not blind replay or expire a fence.
5. **I05 two-writer safety:** two synthetic owners/principals/clients and two concurrent writers must not bypass scope, CAS, isolation or a fenced writer epoch; delayed old writer after leadership/lock expiry cannot publish to the authoritative committed history.
6. **I06 deletion anti-resurrection:** an old, internally valid/authentic archive containing a later confirmed deleted Project must be rejected against a *newer, independently protected* high-watermark/deletion witness; missing, rolled-back or unverifiable witness ⇒ STOP. No new A7 tombstone runtime is being authorized.
7. **I07 verifiable bytes:** exact five-field Markdown UTF-8 bytes including Unicode/code fences/LaTeX and scoped Zotero compound identity/SourceHistory must survive the chosen deterministic future serialization profile; a checksum alone is not provenance/authenticity.
8. **I08 safe recovery:** restore operates only in fresh isolated synthetic staging, checks owner/identity/refs/revisions/keys/authenticity/latest deletion witness; a partial restore or cutover fault cannot write active state. Live cutover needs a *distinct* high-risk approval.
9. **I09 no false external atomicity:** L3's internal transaction cannot automatically commit external blob, cloud manifest or key store. L1's serial HTTP and DAV LOCK/ETag cannot be assumed globally durable/linearizable. Do not use success in an idealized stub as real provider proof.
10. **I10 negative proofs matter:** a positive run without the expected adversarial failure is not evidence. Each case must have independent test oracle, expected reject/STOP, positive control, source SHA/provenance, and expected mutant/fault. Any P0/P1, wrong-scope external traffic or accidental use of real data ⇒ STOP.

**Acceptance formula (planned, not executed):** `KNOWN_FIXTURE_PASS` only if each case's predeclared expected fake IDs and mutations are independently asserted and no false claims; `L1_OR_L3_SYNTHETIC_FEASIBLE_CANDIDATE` only after **ALL mandatory local cases for that route** pass a separate new G1/G2, independent G3 and Design G4, with unsupported production assumptions still recorded. Even two synthetic candidate PASS results do **not** produce `COMPLETE_BACKUP` or `PRODUCTION_RESTORE_CERTIFIED`.

## 4. L3 synthetic transaction-authority experiment (future G1 candidate; no engine chosen)

**Model to validate, not installed:** one logical transaction commits confirmed website-owned data content **AND** authoritative inventory, revisions/relationships, minimal deletion state, operation identity/witness and checkpoint ID. Reader snapshot pins one committed version; updates use adequate constraints/transaction isolation for cross-object invariants. An embedded or server DB could eventually satisfy this, but A36 selects neither.

Proposed positive/negative proof:
- **L3-T01 atomic catalog/write:** crash before commit leaves no visible record/catalog/tombstone; crash after durable commit but lost ACK yields durable operation evidence without blind retry. A false `CONFIRMED` when absent or `DEFINITE_FAILURE` for possibly applied operation FAIL.
- **L3-T02 cross-object invariants:** concurrently unlink/delete Project, edit Note/ReadingStatus and Relink Quote + SourceHistory; either serializable equivalent approved result or detected conflict/abort, no half-commit, no shared Note/Quote deletion.
- **L3-T03 snapshot consistency:** interleave export cursor and concurrent writer; record catalog versions, ensure every listed ID/revision is fetched from *same* snapshot, correct known inventory, no phantom omissions/mixed revisions; invalid state FAIL without output certificate.
- **L3-T04 restore independent rollback:** old signed/encrypted archive and entire transaction store rollback simulated; use externally independent newer T3 fake witness to block deleted Project resurrection. If rollback affects T3 as well or no T3 is available => **UNSUPPORTED/STOP**, not a pass.
- **L3-T05 migration/profile and recovery:** compare exact A6 logical graph/byte profile and isolated stage with protected live state; still cannot claim production cutover, BACKUP key custody or actual DB backup by prototype success.

**Hard caveat:** snapshot isolation alone is not a promise of all cross-object write invariants; test write skew, constraint conflicts and handling of serialization aborts **without auto-replaying an uncertain externally visible write**. If a future chosen engine cannot bind catalog and confirmed content in one transaction boundary, the prototype is *not* L3 and requires a new Design decision (possibly L2).

## 5. L1 synthetic fenced writer + commit-log experiment (future G1 candidate; no provider selected)

**Model to validate, not implemented:** one authorized writer epoch and a protected, monotonically fenced committed catalog head; immutable versioned record payloads and append-only intended/committed operation records. An observer must distinguish durable publish from staged payload and detect stale writer after epoch invalidation, process crash, lost ACK and external out-of-band mutation. The writable DAV-like mock must not be trusted merely because it follows desired fixture behaviour.

Proposed positive/negative proof:
- **L1-T01 writer epoch and stale writer:** two clients/instances, lease/epoch rotate, earlier writer resumes after crash/lock expiry; its stale commit is rejected at authoritative storage/commit boundary, not merely by a process-local mutex. Simulated out-of-band writes bypassing app must either be prevented/detected or trigger UNSUPPORTED.
- **L1-T02 intent/payload/catalog ordering:** inject crash at every stage (record PUT, intent append, commit marker, head publish, delete marker) and lost ACK. Only complete committed versions become visible to readers; no split inventory, phantom record, skipped deletion or false success.
- **L1-T03 consistent reader pinned head:** PROPFIND 207 silently omits a record while log's authoritative ID list includes it; export finds/rejects omission and does not self-certify. Concurrent writer must not change data inside pinned immutable checkpoint.
- **L1-T04 safe Unknown and garbage collection:** delayed ACK/ETag ambiguity keeps `UNKNOWN` until authentic commit witness; expired token, compaction, tombstone aging, old backup or cleanup cannot reintroduce stale content, delete referenced version or reset protected fence.
- **L1-T05 independent deletion witness and key/restore:** simulate archive rollback after confirmed Project deletion; require independent T3 latest witness and isolated graph restore; absent trustworthy T3 => BLOCK even if every DAV PUT and log read returns 200.

**Hard caveat:** a loopback mock that provides ideal compare-and-swap / fence does **not** demonstrate real provider reliability. If strong durable fencing/atomic committed head cannot be established under realistic failure and out-of-band writer cases, `L1_UNQUALIFIED_FOR_Q1e_CERTIFICATION`. Do not silently adopt another backend or request ACCESS-02. A36 **does not** authorize testing a real DAV server.

## 6. Deliberate boundary of isolated deletion witness and rollback proof

**T3 contract as a future test double:** a monotonic source of truth **independent of the archive and rollback target** that authenticates owner, checkpoint epoch, confirmed deletion set/high-watermark and permitted restore origin; no self-report from the restoration archive. In a synthetic test, place T3 in a logically distinct fault domain and simulate rollback of T1/T2 while T3 remains newer, then show **RESTORE_BLOCKED_STALE_DELETION_STATE**. Reverse test: roll back/erase T3 too; result **WITNESS_UNVERIFIABLE / STOP**, not safe restore. **This models a requirement only**—it does not prove physical independence, operational durability or solve retention/privacy. The mechanism, custody, signature key, monotonic hardware, provider and deletion retention remain TBD.

**Do not misstate logic:** if a committed deletion and witness advance cannot be ordered/atomically reconciled under crash, the complete backup and restoration certificate remains blocked; a hash chain whose anchor lives inside the old archive is vulnerable to rollback. Test a valid but stale authenticated backup and marker missing/old, not only corrupted archives.
